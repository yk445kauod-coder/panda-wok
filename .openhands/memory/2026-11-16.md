# 2026-11-16 — panda-wok

## Console alert poll: Server Action → GET route (commit 581c5aa)

**The bug (measured, not theorised).** The console's pending-order poll called a **Server
Action** (`listPendingOrderAlertsAction`). A Next Server Action is a **POST back to the page the
tab is currently on** — not to an API path. Every `/admin/*` route is a static shell, so that POST
landed on a static document and did one of three things:

| outcome | count /7d | why |
|---|---|---|
| 200 | 3,451 | App Router ran the full pipeline to re-emit the static doc |
| 404 | 352 | the action id is not in the prerendered page's manifest |
| 503 | 210 | exceeded Free's 10 ms CPU cap → **Error 1102** |

**4,028 POSTs against 48 orders in the database.** The watcher is mounted in `AdminShell`, so it
fired on *every* console page, in *every* open tab, for *every* admin — which is exactly the
reported symptom ("the admin page is heavy, and requests exceed when more than one admin is
signed in").

**How it was found.** `POST /admin/orders` showed 3,451+352+210 in
`httpRequestsAdaptiveGroups` grouped by `clientRequestPath` **with no method field available**
(`clientRequestHTTPMethod` is not a valid dimension — group by path+status and infer). A POST
appearing on a path that only ever serves a static GET is the tell.

**The fix.** `GET /api/admin/alerts` (gated `adminJson("orders.view")`, one indexed read of
`new` orders). `ops-sync.ts` now `fetch`es it; a 401/403 dispatches `panda-wok:locked` like every
other console read. Deleted `src/lib/actions/order-alerts.ts`.

**Rule for the whole console:** never poll via a Server Action. An action POSTs to the *page*; a
static shell has no handler there. Poll a `route.ts` GET.

## Second read of the same queue (commit 740b7e6)

`/api/admin/session` already returns `pendingOrders`, and the shell fetches it on every page
load. The shared store then did its own opening read of `/api/admin/alerts` — the identical
list, a second Worker invocation per page load per open tab. Fixed by seeding:
`seedOpsPending()` (in `ops-sync.ts`) is called from `AdminApp`'s session handler before the
shell mounts, and `startPolling()` now reads only `if (!store?.loaded)`.

**It overwrites, it does not early-return.** After a lock the shell unmounts, the poll stops,
and the store still holds the pre-lock list; the watcher renders `shared ?? seed`, so an early
return would keep showing the stale queue after re-unlock.

Net effect of the whole session on a console page load: **4 requests → 2** (session + one
page-data read; the queue rides along in the session).

## Console dictionary split (commit 5acbbaa, deployed)

The console SPA rendered the **full** dictionary — 27 blocks — but can only resolve
`common`, `errors`, `kds`, `admin`. The other 23 are storefront copy it never reads.
Measured: the full Arabic `ar.ts` block was a **26,694-byte brotli** chunk in the first
load of every console page.

Fix: `src/lib/i18n/dictionaries/console-en.ts` / `console-ar.ts` hold the four blocks;
`en.ts` / `ar.ts` spread them back (`...consoleEn`), so keys keep one source. `admin-i18n.tsx`
imports the slice; the general `i18n-provider.tsx` no longer imports `en` by value (its
outside-provider fallback used `dict: en`, and `useI18n().dict` has **no reader** — verified by
grep — so the fallback now returns `{}` and the full dict leaves the console graph).

**Live /admin first-load: 247,600 -> 238,548 br, -9.0 KB (-3.7%)**, same 16 chunks. Key count
unchanged: 630 (full) + 1,174 (slice) = 1,804 leaves; `i18n-parity` still green.

Note the honest number: the *admin* block is itself 46 KB raw / ~30 KB br, so the slice is still
big. The win is dominated by evicting the 26.7 KB Arabic chunk and the storefront blocks; the
remainder the split removes is small relative to the admin block.

Guards: `tests/i18n-console-slice.test.ts` (slice == exactly those 4 blocks, byte-identical to
full dict); `tests/admin-weight-budget.test.ts` now fails if any `src/components/admin` file
imports the full dictionary by value.

**Trap hit twice:** the `console-*.ts` split initially broke tsc — the object-member extractor
must skip `//` and `/* */` comments and track brace depth from `export const`; a naive
top-level-key grep also matched nested `{` at 2-space indent (e.g. a nested `nav`), so the real
key set was 27, not 33. Use `/tmp/split.py`-style balanced parsing, never indentation regex.

## Dish-photo storage: DBByte REST gateway -> DBByte S3 (session, uncommitted)

The owner asked to move the menu-photo store to S3, and supplied the DBByte S3
credentials (`https://s3.dbbyte.com`). The store was already DBByte — but via its
proprietary REST gateway (`api.dbbyte.com/storage/<bucket>/upload|download` with a
`Bearer` key). This session moved both sides onto the **standard S3 protocol**.

**Credentials:** owner-supplied, stored in `.env.local` (gitignored) and as Worker
secrets — never in a tracked file. The access key id (`dbs_...`) is an identifier and
ships in `wrangler.jsonc`; the secret half is a `dbk_...` string.
**The key is 52 characters.** A short form fails with `SignatureDoesNotMatch`; the
owner's "renewed" suffix is part of the same string, not a second key.
- endpoint `https://s3.dbbyte.com`, region `us-east-1`, bucket `panda-wok-media`,
  `forcePathStyle: true`.

**SigV4 is done with `aws4fetch` (now a direct dep), not the AWS SDK.** It is ~1 KB,
zero dependencies, Web Crypto based, and works unchanged in both a Cloudflare Worker
and a Next server action. `@aws-sdk/client-s3` is only present transitively (via
`@opennextjs/aws`) and is far too heavy for the 10 ms-CPU media worker.
`aws4fetch` signs in-process and then calls the **global** `fetch`, so a test can
`vi.spyOn(globalThis, "fetch")` and read the signed `Request` (url + `authorization`).

**Files changed (all uncommitted):**
- `workers/media-proxy/src/index.ts` — read path is now `s3.fetch(<endpoint>/<bucket>/<name>)`.
  `x-media-source` is `dbbyte-s3`. Cache/purge/health/name-validation unchanged.
- `src/lib/actions/storage.ts` — upload is now a signed `PUT` of `file.arrayBuffer()`.
- `workers/media-proxy/wrangler.jsonc` — `DBBYTE_ENDPOINT=https://s3.dbbyte.com`,
  `DBBYTE_ACCESS_KEY_ID` as a plain var; `DBBYTE_SECRET_ACCESS_KEY` stays a secret.
- `.env.local` / `.env.example` — `DBBYTE_ACCESS_KEY_ID` + `DBBYTE_SECRET_ACCESS_KEY`
  replace `DBBYTE_KEY`.
- tests, `docs/media-storage.md`, `package.json` (`media:secret`), deploy workflow.

**The bucket is private** — an unsigned GET is `403`, so the media worker's signature
is the only public read path. Do not "fix" a 403 by making the bucket public.

**Deploy needs the secret in two places.** `deploy-pages.yml` now has a
"Set the media worker's S3 secret" step and a "Sync dish-photo storage secrets to
Pages" step, both reading the repo secret `DBBYTE_SECRET_ACCESS_KEY` and warning
(not failing) when it is unset. **An owner must add `DBBYTE_SECRET_ACCESS_KEY`
(and optionally the `DBBYTE_ACCESS_KEY_ID` variable) at the repo settings** — the
integration token here cannot (`secrets: write` is 403, same as the earlier
`CLOUDFLARE_API_TOKEN` case).

**Verified live, not assumed:** two round trips against the real bucket — the real
`uploadMenuImageAction` PUT an object (S3 HEAD 200) that the real worker handler then
served byte-identical, and a missing object returned a clean uncached 404. Bucket
returned to its original 3 test objects, 0 leftovers. typecheck PASS, 20/20
storage+media tests, `next build` green, media worker dry-run 15.6 KiB / 4.93 KiB gzip.
One pre-existing unrelated failure (`tests/field-contrast.test.ts` reads a file deleted
in `e10383b`); the full suite is 488 passed / 1 failed / 18 skipped.

**Not done (deliberate):** the 90 legacy Supabase-Storage objects are NOT migrated —
