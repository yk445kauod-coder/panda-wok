# 2026-11-14 — console heaviness + Worker request volume

## Root causes found (evidence-based)
- **640 KB Supabase client on every admin page.** `src/lib/live/use-ops-signal.ts`
  statically imported `@/lib/supabase/client`, so `@supabase/supabase-js`
  (auth+PostgREST+Realtime) was in the first-load bundle of *every* /admin page,
  for a realtime nudge the poll already covers. Chunk `3923s7wqrhf4b.js` = 640 KB.
  Fixed by `import()` inside `connect()` (commit 7d9a092). Measured live:
  /admin/orders first-load 1612 KB → 843 KB (−48%); chunk gone from the shell.
- **Double ping per order action.** `ops_orders_signal` (orders) + `ops_order_status_signal`
  (order_status_history) both fire on one status change → 2 broadcasts ms apart.
  The shell `OrderAlertWatcher` read on *every* ping (no coalescing) → 2 Worker
  invocations per tap per tab. Fixed with a 300 ms debounce (commit e7b73f4).

## The console is ALREADY a static SPA — verified 2026-11-14
- Every `/admin/*` route is in the build's **prerender-manifest `routes`** (18 admin routes), and
  **no admin route is in `dynamicRoutes`**. Live headers: `/admin` → `x-nextjs-prerender: 1,1`,
  `x-nextjs-cache: HIT`. So the Worker does NOT server-render the console; conversion landed in
  commits `da70e33` + `e53737a` (spec: `.openhands/memory/spa-conversion-spec.md`).
- **The remaining admin CPU cost is `/api/admin/*` (JSON) + middleware**, not SSR.
  Live TTFB: `/api/admin/kitchen` 1.6 s, `/api/admin/session` 0.96 s, `/api/admin/orders` 0.70 s.
  Cloudflare `pagesFunctionsInvocationsAdaptiveGroups` (Nov 14, prod):
  **p50 CPU = 11 830 µs, p99 = 574 603 µs** → still 1000×+ over the Free 10 ms cap.
- Errors Nov 14 = **74** (vs ~1300 on Nov 13) — big drop, but not zero. Hour 14:00 alone = 60.
- **Middleware fix (commit 1e98108):** `updateSession` (JWT verify + possible round trip) ran on
  every request *before* the admin check, and the admin branch then **discarded that response**
  (`response = NextResponse.next(...)`). Console never reads the customer session (gate cookie
  auths it; `x-pw-path` elevates reads), so the refresh was pure waste on the most CPU-tight
  surface. Now skipped for admin only. Note: this is a *micro*-optimisation — the real fix for
  Error 1102 is Workers Paid (5 min CPU) or moving the data layer off the Worker.

## Staff login "حدث خطأ ما" — root cause + fix (2026-11-14, later)
- Symptom: intermittent generic error on the staff login button (owner passcode fine).
  Reproduced only sometimes → classic 1102 (10 ms CPU cap), not a logic bug.
- **Root cause:** `unlockAdminAction` did the gate cookie AND `mintStaffSession`, which is
  a chain of ~4 Supabase round trips (profiles read → generateLink(magiclink) →
  verifyOtp → client getUser). On Free plan that chain tipped the *login request itself*
  over the cap. Supabase auth logs confirmed the mint chain ran fine (all 200) — the
  Worker request was what died.
- **Fix (commit a1a45bd):** unlock returns as soon as the gate cookie is set; new
  `POST /api/admin/session/upgrade` (gated on the unlock cookie, no-op once
  `panda-wok.admin-minted`=1) does the mint in the background; `AdminApp` calls it when
  `payload.unlocked`. Degrades to broadcast + poll if it fails. Also removed
  `revalidatePath("/", "layout")` from both gate actions — the console is a static shell,
  so invalidating every prerendered page on each lock/unlock was pure Worker work.
- `tests/admin-live-signal.test.ts` updated to pin the new location (unlock must NOT
  reference mintStaffSession; upgrade route + AdminApp must).

## Console realtime + iOS audio (2026-11-14, verified live)

**Root cause of "orders don't appear until I refresh".** `use-ops-signal.ts` chose
`postgres_changes` whenever a Supabase session existed. A live probe (anonymous
socket, node + @supabase/supabase-js) proved that branch **reports SUBSCRIBED while
delivering zero events**, while the public `ops-orders` **broadcast arrives fine**.
So `live` flipped true → boards' fallback poll relaxed 8 s → **120 s** → freeze.
Fix: subscribe to the broadcast **only**; never `postgres_changes`. Live-verified:
a new order appeared in **6 s** (under the 60 s poll). Poll now relaxes to 60 s, not 120 s.

**The staff-session mint was removed entirely** (browser held a staff token it did
not need; mint also cost ~2 Supabase round trips on login). Deleted
`/api/admin/session/upgrade`; `staff-session.ts` keeps only `MINTED_COOKIE` +
`endMintedSession` to clean up old browsers. Do **not** reintroduce a mint to
enable `postgres_changes` — the probe above shows it does not work anyway.

**iOS/Safari audio (3 real defects, all fixed):**
1. Gate form called `window.location.reload()` after unlock → destroyed the user
   activation → WebAudio refused to start → siren silent for anyone who just logged
   in. Now re-resolves the session in place (`onUnlocked` prop).
2. Safari's **`interrupted`** AudioContext state (call/Siri/lock/background) is
   neither `running` nor `suspended`; a `suspended`-only resume check skipped it.
   All resumes go through `ensureRunning()` = resume on **any non-running** state.
3. `navigator.audioSession.type = "playback"` (Safari 16.4+) — the only way to stop
   the **iPhone mute switch** from silencing WebAudio. Re-asserted on every gesture
   and on `visibilitychange`→visible.
Gotcha found by a test: `ensureRunning(ctx, finish())` is an **eager call** — pass
the function ref (`finish`), not its result.

**Traffic, measured via CF GraphQL** (`pagesFunctionsInvocationsAdaptiveGroups`):
12.6k req on 11-12, **23.7k on 11-13** for ~1 admin (≈16 req/min) — the 8 s poll on
every admin page. Free plan = 100k/day.

**Lesson:** `SUBSCRIBED` is not delivery. Always probe the real socket before
trusting a realtime branch; a silent channel that "connects" is worse than none.
