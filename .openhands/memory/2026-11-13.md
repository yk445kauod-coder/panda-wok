## Root cause of 1102 is architectural, not (only) Intl (2026-11-13, later)

Measured with `wrangler tail --format=json` on the live Worker (`panda-wok.yk445kauod.workers.dev`):
- **Workers Free = 10 ms CPU/request, hard kill → Error 1102.** Confirmed in Cloudflare docs.
- Live CPU per invocation: warm **17–110 ms** (p50 ~25 ms), cold **~560–1100 ms**.
  GraphQL `workersInvocationsAdaptive` for the day: cpuTimeP50 = **321 858 µs (322 ms)**, P99 = **882 762 µs**.
  → EVERY dynamic request blows the 10 ms cap; 1102 is guaranteed, not load-dependent.

Why "dozens of similar projects never hit this": those are static/Vite/SPA on Pages (assets served by the
edge, **no Worker invocation**). This project is **Next 16 + OpenNext SSR** → every navigation runs a ~9 MB
`handler.mjs` in a Worker. The 10 ms cap is a property of SSR-on-Workers-Free, not of this app's code.
The Intl caching shaved the app's own CPU but cannot get a full React SSR render under 10 ms.

Structural fixes (in order of leverage):
1. **Workers Paid ($5/mo)** → CPU cap 10 ms → 5 min. One line, ends 1102 permanently. Recommended.
2. Keep dynamic routes off the Worker (static export / ISR where possible).
3. Edge-cache the public HTML (already in `scripts/pages/edge-cache.js`; verified working: `/menu` GET →
   `x-edge-cache: HIT`, `s-maxage=600, stale-while-revalidate=86400`). Admin is never cacheable → always SSR.
4. Cut cold-start: 9 MB bundle + no dynamic-import splitting of heavy admin-only modules.

Note: `curl -I` sends HEAD (not cacheable → shows MISS/`no-store`); must use `curl -D- -o /dev/null` (GET).

## WHY every page is SSR (the real 1102 lever) — found 2026-11-13
- **Every public page has `export const dynamic = "force-dynamic"`** (home, about, contact, faq, location,
  privacy-policy, menu) and the admin tree is dynamic too (26 admin pages + layout).
- Reason: each page calls `getLocale()` (cookies/headers → request-time) + `getPublicSettings()` and renders
  translated copy server-side. So NO public page is prerendered (0 `.html` in `.next/server/app/(site)/*`).
- Consequence: the Worker runs a full React SSR on every visit; the edge cache only masks repeat visits.
- To "remove SSR": public pages must become static per locale. Server-rendered copy cannot switch language
  on the client (provider `t()` only translates client-component strings), so bilingual static REQUIRES a
  per-locale build (locale in URL, or middleware rewrite `/about` → `/_static/{locale}/about` with
  `generateStaticParams`). That is the decision the owner must make (SEO surface / canonical URLs).
- Admin (26 pages, RBAC, live data) client-side rewrite is larger and security-sensitive (admin reads via
  anon key are RLS-bound; admin data needs authenticated admin sessions).

## "Remove SSR everywhere" — architectural blockers (verified 2026-11-13)
Scope: 16 public pages under `src/app/(site)` + 26 admin pages under `src/app/admin` + `src/app/layout.tsx`.

1. **Admin CANNOT fetch Supabase from the browser.** Admins authenticate with a *passcode / staff login-id*
   HMAC cookie (`src/lib/auth/admin-gate.ts`, cookie `panda-wok.admin`, default passcode `Panda2026`) — there
   is **no Supabase auth session** for staff. So `createServerSupabase()` (`src/lib/supabase/server.ts`)
   elevates every `/admin` request (flagged by the middleware `x-pw-path` header) to the **service-role** key,
   because the staff RLS policies resolve through `auth.uid()` and would authorise nothing. The service key is
   server-only and must never reach the browser. => Admin-off-Worker requires a **server-side proxy**: browser
   calls same-origin API routes (`/api/admin/*`) carrying the gate cookie; the route authenticates the gate and
   queries with the service role. Only 1 API route exists today (`/api/analytics`); everything else is a Server
   Action (15 `"use server"` files). Big, security-sensitive rewrite.

2. **The ROOT layout reads cookies.** `src/app/layout.tsx` calls `getLocale()` (cookie → session → Accept-Language)
   and wraps everything in `I18nProvider locale/dict` + sets `<html lang dir>`. A root layout that reads cookies
   makes **every route dynamic**. To remove SSR the locale must move to the client.

3. **Server pages render localized copy server-side.** ~16 public pages call `getLocale()`/`getT()` and print
   translated strings directly in the RSC output (78 call sites). Those strings cannot re-translate on the client
   (the provider's `t()` only covers client components). => bilingual static needs either locale-in-URL
   (`/en/...`,`/ar/...`) or a middleware rewrite to per-locale static trees.
   - Fast subset: `about`, `faq`, `location`, `privacy-policy` are `force-dynamic` only because of
     `getLocale()`+`getPublicSettings()` (no `searchParams`, no cookies) → easiest to make static.
   - `menu`, `menu/[slug]`, `home` also fetch DB + call `getLocale()`; `cart`/`checkout`/`orders`/`account`/
     `feedback`/`chat` are genuinely personal/dynamic (need the user session).

## ROOT CAUSE of the total outage + fix (2026-11-13 late, verified live)

**The whole site (public + admin) was DOWN with 1102, not just heavy admin pages.**
Earlier in this session every public route 503'd. Cause was NOT page weight:

1. Commit `6294884` ("Prerender customer site per locale under /[lang]") made the
   site prerender — `.open-next/cache/` holds 229 pages keyed by build id.
2. **The deploy never shipped those pages to production.** `scripts/build-pages.mjs`
   never ran OpenNext's `populateCache`, and our resilient wrapper renamed the cache
   (`name: "panda-wok-resilient-kv"`), so `populateCache` skipped the KV upload even
   when called (`Incremental cache does not need populating`). KV had ZERO build-id
   keys → every production request did a from-scratch React SSR → exceeded the
   **10 ms free-plan CPU cap** → 1102 on every page.

**Fix (commit 54f8461, deployed `c08eb064`):**
- `src/lib/cache/incremental-cache.ts`: adopt the stock KV cache name
  (`NAME` = `cf-kv-incremental-cache`) so `populateCache` recognises it, AND read the
  **static-assets cache** (prerendered pages bundled under `cdn-cgi/_next_cache`) when
  KV misses. KV stays first so revalidation still wins.
- `scripts/build-pages.mjs`: `cp .open-next/cache .pages/cdn-cgi/_next_cache` — a plain
  copy, **no KV writes**, so the site survives a cold KV / spent KV write quota.
- `package.json` `pages:deploy`: run `populateCache remote` (best-effort) before deploy.

Result: `/en` 40/40 sequential + 10/10 concurrent = 200. All public pages 200.
**This disproves the earlier "no code change fixes 1102 on Workers Free" note** — for
*prerendered* pages it does.
